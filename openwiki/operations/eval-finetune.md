# Evaluation & Finetuning

## Dataset Evaluation

### Running Evaluation

```bash
agentforge eval \
  --agent-dir agents/<id> \
  --dataset agents/<id>/eval_dataset.yaml
```

### Dataset Format

YAML file with a `cases` list:

```yaml
cases:
  - input: "How is the server health?"
    notes: "should collect real data before responding"
  - input: "Are there errors in the latest system logs?"
    notes: "should use read_log_tail"
```

Each case has:
- `input`: The prompt to send to the agent
- `notes`: Human notes about expected behavior (not enforced programmatically)

### Results

Results are saved to `agents/<id>/eval_runs/<timestamp>.jsonl`, one JSON line per case:

```json
{
  "case": 1,
  "input": "How is the server health?",
  "output": "...",
  "notes": "should collect real data before responding",
  "latency_ms": 12345,
  "timestamp": "2026-07-09T...",
  "ok": true,
  "judge": { ... }  // if LLM judge is configured
}
```

### LLM Judge

Enable automatic scoring in `agent.yaml`:

```yaml
eval:
  judge_model: "gemma4:e4b"
  criteria:
    - response based on real data
    - objective and actionable recommendation
    - no fabricated metrics
```

The judge model (local Ollama model or Gemini API) scores each criterion from 0-100 and calculates an average.

The judge prompt receives:
- The original input
- The agent's output
- Tool execution evidence (for agents that used tools)
- The criteria to evaluate

### Eval Configuration

The `eval.yaml` generated from the spec includes:
- `eval_version`: Schema version
- `agent_id`: Agent identifier
- `metrics`: Standard metrics (`semantic_quality`, `tool_use_compliance`, `format_validity`, `consistency`)
- `user_feedback`: Scale for human scoring (0-10)
- `notes`: Description of the evaluation scenario

## Benchmark Evaluation

### Benchmark Runner

**Location**: `scripts/run_benchmark_eval.py`

The benchmark runner executes agents across FORGE and REAL scenario datasets:

```bash
python scripts/run_benchmark_eval.py
```

### 4-Stage Benchmark Pipeline

The runner implements the 4-stage funnel:

1. **ABS** — Can the model call tools at all?
2. **LOP** — Does it hold under real operational pressure?
3. **FORGE** — Multi-turn, chained, autonomous work
4. **REAL** — Real browser, real tests, no shortcuts

Each stage is an elimination gate. Models that pass all stages are deployed to agent-FORGE.

### Provider Auto-Management

The benchmark runner automatically:
- Stops/starts Ollama and TurboQuant services based on the configured provider
- Ensures the correct model is loaded for each benchmark stage
- Collects results across all agents

## Finetuning Pipeline

### Overview

AgentForge includes a complete LoRA fine-tuning pipeline built with Unsloth. The pipeline supports synthetic data generation, dataset assembly, training, and quantization.

### Pipeline Stages

```
1. Seed generation (Gemini API)
   → seeds_501_592.json
   → Generates training seeds from existing agent specs

2. Synthetic data generation
   → gen_v3_27b.py — generates training data using qwen3.5:27b
   → gen_v3_overnight.sh — overnight batch generation
   → gen_v3_extension.sh — extension data generation

3. Dataset assembly
   → assemble_v3_dataset.sh — combines synthetic data into final dataset

4. Training
   → train_v3.py — Unsloth LoRA training

5. Quantization
   → quantize_v3.log — quantization logs

6. Evaluation
   → Benchmark results comparing fine-tuned vs base models
```

### Dataset Versions

| Version | Source | Description |
|---------|--------|-------------|
| synth.jsonl | Gemini API | Initial synthetic data |
| synth_agentforge_v2.jsonl | AgentForge agents | V2 agent-generated data |
| synth_v3_27b.jsonl | qwen3.5:27b | V3 data generated by 27B model |
| synth_v3_overnight.jsonl | Overnight batch | Extended V3 overnight generation |

| traces_all_*.jsonl | Benchmark runs | Full trace logs |

### Gemini-Synthetic Data Generation

**Location**: `finetune/gemini_synth/`

Uses Gemini API to generate synthetic training data:

| File | Role |
|------|------|
| `generate_dataset.py` | Main generation script |
| `generate_seeds_lote2.py` | Additional seed generation |
| `AGY_AGENTFORGE_V2.md` | System prompt for Gemini generation (v2) |
| `AGY_AGENTFORGE_V3.md` | System prompt for Gemini generation (v3) |
| `seeds_501_592.json` | Generated seeds |

The generation prompt is defined in `AGY_AGENTFORGE_V3.md` — it instructs Gemini to generate agent behaviors, tool calls, and responses that match AgentForge's operational patterns.

### Fine-tuning Strategy

**Location**: `docs/FINETUNING-STRATEGY.md`

Key principles:
- LoRA fine-tuning (parameter-efficient)
- Unsloth for memory-efficient training
- Synthetic data from real agent behaviors
- Evaluation against benchmark scenarios to measure improvement
- Quantization (AWQ/GGUF) for deployment efficiency

### Evaluation with Fine-tuned Models

Fine-tuned models are evaluated through:
1. **Benchmark runner** — same scenarios as unfine-tuned models
2. **Regression analysis** — comparing v2 vs v3 results
3. **Quantization impact** — comparing full vs quantized performance

The finetune logs directory contains execution logs for all training and generation runs, useful for debugging and reproducibility.
